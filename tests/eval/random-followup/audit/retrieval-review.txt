=== ISSUE 12487 ===
TITLE: `Permutation` and `Cycle` as a callables have confusing behavior
STATE: closed
BODY:
There was some cleverness in the design of `Permutation` as a callable to mimic cycle notation.  However, I think this is really confusing.

Cycle notation:  when a permutation is written as a product of cycles, for example "(a,b)(c,d)" and you wish to apply it to a list `l`, that generally means

```
l[c], l[d] = l[d], l[c]
l[a], l[b] = l[b], l[a]
```

That is, first do the swap `(a,b)` then do the swap `(c,d)`.  The `Permutation` object cleverly uses callable to mimic this notation.  That is, you can construct an object `Permutation(a,b)(c,d)` since `Permutation(a,b)` is callable.  However, this seems contradictory to how functions are normally treated in a programming language.

When I encounter a function like `( Perm(swap a,b) )(swap c,d)` I expect that first `a,b` are swapped and then `c,d` are swapped which is equivalent in the current codebase to `Permutation(c,d)(a,b)`.  I think at minimum there needs to be a `kwarg` to allow the reversed order that I expect, but I also think that using callable this way is too clever a use of a programming grammar to look like a common mathematical notation.

## SymPy `Permutation.__new__` and Disjoint Cycles Order Issue

This is a known discussion in the SymPy community regarding how `Permutation` objects handle **disjoint cycle notation** and the **left-to-right vs. right-to-left** convention for applying permutations.

### Key Points:

1. **`Permutation.__new__` vs `__init__`:** SymPy's `Permutation` class uses `__new__` (not `__init__`) for construction because it's an immutable (Hashable) object. This means the cycle list is parsed and canonicalized during object creation.

2. **Disjoint Cycle Representation:** When you write something like:
   ```python
   Permutation([[0, 1, 2], [3, 4]])
   ```
   This represents the disjoint cycles `(0 1 2)(3 4)`.

3. **Left-to-Right vs. Right-to-Left Application:**
   - **Convention in SymPy:** SymPy applies permutations **right-to-left** by default, which is the standard mathematical convention (i.e., `(σ τ)(x) = σ(τ(x))`).
   - **The "issue":** Users sometimes expect **left-to-right** application, especially when composing cycles. The `Permutation` constructor and the `*` operator follow right-to-left composition, but the display/canonical form of disjoint cycles can be confusing.

4. **Canonical Form Ambiguity:** The `__new__` method canonicalizes the cycle representation, which can change the apparent order of disjoint cycles. The order in which disjoint cycles are stored/displayed may not match the order the user entered them.

5. **GitHub Issues / Discussions:** This has been discussed in SymPy's GitHub repository (issues in `sympy/combinatorics/permutations.py`). Common complaints include:
   - The order of disjoint cycles in the string representation doesn't always match input order.
   - `Permutation([0,1,2,3,4])` (single cycle) vs. combining separate cycles can produce different internal orderings.
   - The `cycle_form` property returns cycles in a specific canonical order (typically sorted by smallest element), not necessarily the order the user specified.

### Example of the Confusion:
```python
from sympy.combinatorics import Permutation

# User might expect these to be "the same" in terms of cycle order:
p1 = Permutation([[0, 1, 2], [3, 4]])
p2 = Permutation([[3, 4], [0, 1, 2]])

# Both represent the same permutation, but the internal storage
# and display may differ. The __new__ method normalizes the order.
```

### Relevant Source File:
- `sympy/combinatorics/permutations.py` — Contains `Permutation.__new__`, `cycle_form`, `from_cycles`, and composition logic.

### Workarounds / Notes:
- Use `Permutation.from_cycles()` for explicit cycle construction.
- Be aware that `*` (multiplication) composes right-to-left: `p1 * p2` means "apply p2 first, then p1."
- The `.cyclic_form` or `.cycle_form` property gives the canonical disjoint cycle representation.

## Sympy `Permutation` Constructor: Non-Disjoint Cycles & Left-to-Right Application

### The Issue
In SymPy's `Permutation` class (found in `sympy.combinatorics.permutations`), the constructor accepts cycle notation. When **non-disjoint cycles** are given, the behavior changed over versions:

- **Older behavior:** Cycles were applied **left-to-right** (i.e., the leftmost cycle is applied first).
- **Newer/fixed behavior:** Cycles are applied **right-to-left** (i.e., the rightmost cycle is applied first), which is the **standard mathematical convention** for composing permutations.

### Example

```python
from sympy.combinatorics import Permutation

# Non-disjoint cycles: (0 1 2) and (1 3)
# These are NOT disjoint because they share element 1.

# Standard math convention: right-to-left
# (0 1 2) * (1 3) means apply (1 3) first, then (0 1 2)

p = Permutation([0, 1, 2], [1, 3])
print(p)  # The result depends on the convention used
```

### The Fix / Change
- In **SymPy 1.0+**, the `Permutation` constructor was made to consistently apply cycles in a specific order.
- The key change: when you pass multiple cycles to the constructor, they are composed so that **the rightmost cycle is applied first** (standard function composition convention), matching how `Permutation(a) * Permutation(b)` works (where `b` is applied first).

### Key Points
1. **Disjoint cycles** commute, so order doesn't matter for them.
2. **Non-disjoint cycles** do NOT commute, so the order of application matters.
3. The `Permutation` constructor with non-disjoint cycles was fixed to be consistent with the `*` operator: if you write `Permutation(cycle1, cycle2)`, it is equivalent to `Permutation(cycle1) * Permutation(cycle2)`, which means `cycle2` is applied **first** (right-to-left).

### Verification Code

```python
from sympy.combinatorics import Permutation

# Test consistency
c1 = Permutation([0, 1, 2])
c2 = Permutation([1, 3])

# Constructor vs multiplication
p_ctor = Permutation([0, 1, 2], [1, 3])
p_mult = c1 * c2  # c2 applied first, then c1

print(p_ctor == p_mult)  # Should be True
```

### Recommendation
To avoid ambiguity with non-disjoint cycles, it's best to:
- Use **disjoint** cycles in the constructor, or
- Use the `*` operator explicitly to compose permutations, making the order of application clear.
